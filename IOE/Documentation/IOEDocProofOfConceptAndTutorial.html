Internet Operating Environment


The Internet Operating Environment (IOE) is an implementation of a protocol for treating independently distributed JavaScript programs as interoperable applications within a common execution environment.
The broader concept and motivation are described in the 'IOE proposal article'.

This document takes a more practical approach: instead of merely describing the protocol, it implements its components step by step through small executable examples.
Each example introduces a specific part of the protocol and can be executed directly from this document, making the page simultaneously a tutorial, technical reference, and proof of concept.
The initial implementation is intentionally small. Its purpose is not to create a complete operating system, but to demonstrate how applications, dependencies, interfaces, and execution environments can be standardized independently of the particular user interface used to run them.

How This Proof of Concept Works


1. The IOE Environment

We begin with a minimal IOE environment. The environment is responsible for providing the facilities through which applications can operate. It is not itself the application. 

HTML Document
      |
      v
+---------------------------+
| Internet Operating        |
| Environment               |
|                           |
|  Application Loader       |
|  Interface                |
|  Application Management   |
+---------------------------+
      |
      v
   Application

The first implementation will intentionally be very small. There is no attempt to create a complete operating system or desktop environment. The objective is to demonstrate the protocol with the smallest practical implementation.


2. The Application

An IOE application is an independently implemented JavaScript program that follows the interface defined by the IOE protocol.

The application should not need to know how the surrounding environment is implemented. In particular, an application should describe what resources or interfaces it requires rather than directly depending on a particular graphical or terminal implementation. 

Application
     |
     |  "I require a text interface."
     v
IOE Protocol
     |
     v
Environment provides the interface

3. The Application Header

Before executing an application, the environment needs information about it. The first prototype will therefore give every IOE application a protocol header.

The header will describe information such as the application's name, version, required interfaces, optional interfaces, dependencies, and, when applicable, graphical window requirements.

For the first prototype, the header will be represented by a JavaScript module returning a JavaScript object. This keeps the application self-contained while retaining a structure that can later be represented as JSON or another machine-readable format. 

export const IOE_Application =
{
    header:
    {
        name: 'Hello World',
        version: '0.1',

        interface:
        {
            required:
            [
                'text'
            ]
        },

        dependencies:
        [
        ]
    },

    run: function(a, b) { return('Hello World! a + b = ' + (a + b)); }
};

4. Interface Requirements

The protocol will distinguish between an application's requirements and the implementation used to satisfy those requirements.

For example, a program may require a text interface without requiring a specific terminal emulator. Another program may require a graphical window without requiring X11, Wayland, SDL, Canvas, or any other particular window system. 

Application
     |
     |  requires: WINDOW
     v
IOE Interface
     |
     +-------------------+
     |                   |
     v                   v
HTML Canvas          Native Window

This separation is important because the same application should be capable of operating under different implementations of the IOE environment.


5. Text Applications

The first application will be a simple "Hello World" program that uses the text interface.

The purpose is analogous to a conventional command-line program: it does not request a graphical window merely to print text. An IOE implementation could provide this interface using an ordinary HTML element, such as a <span>, while another implementation could display the same output in a terminal, console, or native text interface. 

IOE Application
      |
      v
   TEXT API
      |
      +-------- HTML <span>
      |
      +-------- TUI
      |
      +-------- Native terminal

6. Graphical Applications

Later examples will demonstrate applications that require a graphical window.

Such an application will declare its graphical requirements through the protocol. It may also describe the desired configuration of its window, such as its dimensions, title, and whether it can be resized. 

  {
    interface:
    {
        required: ['window']
    },

    window:
    {
        width: 640,
        height: 480,
        resizable: true
    }
  }

The application does not need to determine how this window is created. An IOE implementation could use an HTML Canvas, another HTML element, a native window system, SDL, or another suitable mechanism.


7. Dependencies

The protocol will also allow applications to declare dependencies. This provides a way for independently developed JavaScript libraries and headers to become components of an IOE application.

For example, an IOE application could use a library from my 'JSHeaders' directory while simultaneously depending on IOE-specific functionality. 

IOE Application
      |
      +---- IOE Includes
      |
      +---- JSHeaders
      |       |
      |       +---- ysxColor
      |       +---- ysxDraw
      |       +---- ysxGeoPlot
      |
      +---- Application Code

This will allow the proof of concept to demonstrate not only application execution, but also the possibility of a distributed ecosystem in which independently maintained components can be combined.


8. The Execution Process

The complete process can therefore be summarized as follows: 

1. Locate an application
        |
        v
2. Load its protocol information
        |
        v
3. Read the application header
        |
        v
4. Determine its requirements
        |
        v
5. Compare requirements with
   the capabilities of the environment
        |
        v
6. Load the application
        |
        v
7. Initialize the application
        |
        v
8. Provide its requested interfaces
        |
        v
9. Application executes

This sequence will be implemented incrementally. Each step will first be demonstrated independently before additional functionality is introduced.

Wrapping Existing JavaScript

  
  

    An important property of the IOE protocol is that an application does not necessarily have to be written specifically for IOE. Existing JavaScript code can instead be wrapped by an IOE application interface.

    To demonstrate this, the following example does not load another JavaScript file. Instead, a simple existing JavaScript function is defined directly in this document and then wrapped by an IOE_Application object.

    The original function has no knowledge of IOE. The wrapper provides the metadata required by the protocol and connects the IOE run() operation to the existing function.
  


  

    function HelloWorld(a, b) { return( "Hello World! a + b = " + (a + b)); }

    const IOE_Application =
    {
    header:
    {
      name: "Wrapped Hello World",
      version: "0.1",

      interface:
      {
        required:
        [
          "text"
        ]
      }
    },

    run: function(a, b) { return(HelloWorld(a, b)); }
    };
  


  

    The IOE can now interact with IOE_Application in exactly the same way as it interacted with the previous Hello World application.

    The difference is that the actual application logic was not written as part of the IOE protocol. It was simply wrapped by it.
  


  

    const Result = IOE_Application.run(10, 20);
    document.getElementById("SpanTerminal").innerHTML = Result;
  


  

    This distinction is important: IOE is intended to provide an interoperability layer for existing JavaScript code, rather than requiring every application to be rewritten as an IOE application from the beginning.
  










  

  
Dependencies


  

    An IOE application may depend on JavaScript code that is not part of the application itself. Instead of requiring the application to directly import that code, the application can declare its dependencies in its header.

    This allows the IOE to resolve the required modules before the application is executed. The dependency mechanism therefore separates two different requirements: an interface describes a capability that the IOE environment must provide, while a dependency identifies external code required by the application.
  

  
  
dependencies: [ { name: 'ysxTRI_Triangle', url: '/JSHeaders/ysxMath/Geo/ysxTri.js' } ]


  

    The following example uses the existing ysxTRI_Triangle class as a dependency. The class was not created specifically for this IOE example. The IOE application simply declares that it needs the class and uses it to implement a triangle calculator.

    Three values are supplied by the user: the sides a and b, and the included angle gamma.

    The application constructs a triangle using the resolved dependency and returns the information generated by its CoutInfo() function.
  


  

  const IOE_Application =
  {
    header:
    {
      name: 'Triangle Calculator',
      version: '0.1',
      interface: { required: [ 'text' ] },
      dependencies: [ { name: 'ysxTRI_Triangle', url: '/JSHeaders/ysxMath/Geo/ysxTri.js' } ]
    },
    
    run: function(a, b, gamma, dependencies)
    {
      const Triangle = new dependencies.ysxTRI_Triangle(a, b, gamma);
      return(Triangle.CoutInfo());
    }
  };
  


  
The important point is that the triangle class itself has not been converted into an IOE application. It remains an ordinary JavaScript module. IOE provides a mechanism for existing code to become part of an application through a declared dependency.


  
The resulting execution flow is therefore:

  

    IOE application
    |
    v
    declares dependency ysxTri.js
    |
    v
    provides ysxTRI_Triangle
    |
    v
    IOE resolves dependency
    |
    v
    Triangle Calculator
    |
    v
    constructs triangle
    |
    v
    CoutInfo()
    |
    v
    text interface
  


  
This is an important part of the interoperability model of IOE. Existing JavaScript libraries do not need to be rewritten merely because an IOE application wants to use them. The IOE application can act as the protocol-level wrapper around existing code.

Application Inputs and Interaction


  

    When an IOE environment loads an unknown application, it cannot assume how many inputs the application requires.

    The number of JavaScript function parameters is also insufficient to describe an application's input requirements, because a parameter does not specify what the value represents, what type it has, or how the environment should obtain it.

    IOE therefore allows applications to declare their inputs in the application header.
  


  

  inputs:
  [
    { name: 'a', type: 'number' },
    { name: 'b', type: 'number' },
    { name: 'gamma', type: 'number' }
  ]
  


  

    The application can then request these values through the IOE input interface rather than accessing HTML elements directly.
  


  
run: function(IOE)
  {
    const a = IOE.input.number('a');
    const b = IOE.input.number('b');
    const gamma = IOE.input.number('gamma');
    ...
  }
  


  

    This separates the application from the implementation of the user interface. In the current HTML proof of concept, IOE.input.number() reads from an HTML <input> element.

    A different IOE implementation could instead obtain the same value from a terminal, a graphical control, a remote interface, or another input mechanism.

    

    The IOE can also generate the required controls from the application's input declaration. Consequently, the documentation does not need to know whether an application requires one input, three inputs, or many more.

    The application describes its requirements and the IOE creates the corresponding interface.

    

    The triangle calculator demonstrates this mechanism using the existing ysxTRI_Triangle class. Its three values, a, b, and gamma, are declared by the application and obtained through the IOE input interface.
  


  
Application
    |
    | declares inputs
    v
IOE header
    |
    | generates interface
    v
HTML input controls
    |
    | user supplies values
    v
IOE.input.number()
    |
    v
Application.run()
    |
    v
ysxTRI_Triangle
    |
    v
CoutInfo()
    |
    v
text interface


  

    This mechanism also provides a foundation for interactive applications.

    The current implementation reads values that are already present in the generated controls, but the same interface can later be implemented as an interactive request mechanism similar to std::cin in C++.

    The application would continue to request a value through the IOE interface while the environment determines how that value is obtained.

Demonstration of IOE Capacities and Use Cases Through 'NetShell'

  

  So far, this document has demonstrated the fundamental mechanisms of IOE:

  
    
  
  • applications can describe themselves through an IOE header;
    • 
    
  • an IOE environment can determine what an application requires;
    • 
    
  • dependencies can be resolved independently of the application;
    • 
    
  • input can be provided by the environment rather than being tied to a particular user interface;
    • 
    
  • existing JavaScript code can be wrapped and exposed as an IOE application;
    • 
    
  • and the application itself does not need to know which particular interface is providing its environment.
    • 
  

  



  These examples demonstrate that the protocol works.

  However, this raises a more important question:

  What can this actually be used for?

  

  A protocol should not exist merely because it can be implemented. If IOE is to become useful, it should make possible forms of interaction with Internet resources that are difficult, inconvenient, or conceptually different from ordinary web browsing.

  The next step is therefore not another isolated protocol example. It is the construction of a practical environment that demonstrates what can be done with the protocol.

  

  
NetShell

  

  For this purpose, this project introduces NetShell.

  

  NetShell is a terminal-oriented interface built on top of IOE. Its appearance and interaction model are inspired by classic DOS terminals, while its command conventions are primarily derived from modern Unix / Linux environments.

  The combination is deliberate.

  The terminal provides a familiar and extremely lightweight way of interacting with computational resources, while the underlying filesystem, application system, and execution model are provided by the NetShell environment rather than by IOE itself.

  

  The distinction is important:


  
                   IOE
                    │
       Application interoperability
                    │
        ┌───────────┴───────────┐
        │                       │
  IOE Applications       IOE Interfaces
                                │
                        ┌───────┴───────┐
                        │               │
                     NetShell        Other
                                    environments
  


NetShell is therefore not part of the IOE protocol.

It is one possible environment built using IOE.



A different developer could create a graphical environment, a canvas-based environment, a remote application browser, an embedded environment, or something that does not resemble a traditional operating system at all.

This separation is one of the central properties that IOE is intended to preserve.




Why a terminal?



A terminal makes the relationship between the user, the environment, IOE, and an Internet application particularly visible. It is also simpler to program and enough to showcase the capabilities of the IOE.

For example, the user may eventually be able to write:


$ ls

HELLO.APP
TRICALC.APP
TRICLASS.JSM

$ tricalc 3 4 1.5707963268



The command itself is simple. What happens behind it is more interesting.

NetShell can interpret `tricalc` as an application in its virtual filesystem, locate the corresponding Internet resource, ask IOE to load the application, resolve its dependencies, provide its execution environment, and return its result to the terminal.



Conceptually:


User command
     │
     ▼
NetShell
     │
     ├── command interpretation
     ├── virtual filesystem
     └── application lookup
             │
             ▼
            IOE
             │
             ├── application loading
             ├── dependency resolution
             ├── interface/environment
             └── execution
             │
             ▼
       IOE Application
             │
             ▼
          result
             │
             ▼
          NetShell
             │
             ▼
           user



This is substantially different from merely putting a JavaScript function inside a web page and calling it.

The terminal becomes an interface through which Internet-distributed software can be treated as computational resources.




NetShell's filesystem



IOE itself does not require a filesystem.

A filesystem is a decision made by an environment.

My page will nevertheless provide a small hard-coded virtual filesystem for the NetShell because it gives applications and resources a familiar organization and gives users a practical way to discover and execute them.

The initial filesystem will intentionally be minimal.



For example, an entry may be represented conceptually as:


{
  name: 'TRICALC.APP',
  path: '/IOE/Examples/DynamicInputs.js',
  type: 'application'
}



or:



{
  name: 'TRICLASS.JSM',
  path: '/JSHeaders/ysxMath/Geo/ysxTri.js',
  type: 'module',
  class: 'ysxTRI_Triangle'
}



`name` and `path` identify the resource and are fundamental to the filesystem.

Other properties, such as `type` and `class`, provide information understood by the current NetShell implementation.

The filesystem may also contain additional metadata that NetShell does not currently understand. Unknown properties should not automatically make an entry invalid. This allows the filesystem format to evolve without requiring every environment to understand every possible property.

The `.APP` and `.JSM` names are semantic names used by NetShell. They do not imply that the underlying Internet resource must physically use those extensions.



For example:


TRICALC.APP
       │
       ▼
/IOE/Examples/DynamicInputs.js



and:



TRICLASS.JSM
       │
       ▼
/JSHeaders/ysxMath/Geo/ysxTri.js



The virtual filesystem therefore provides a layer of organization over the underlying Internet resources.




NetShell commands



The initial command set will intentionally remain small.



The first version can provide commands such as:


ls
cd
pwd
clear
help
echo



and application execution through the application's name:



tricalc 3 4 1.5707963268



There is no need for an `exit` command in the initial browser-based environment. The NetShell interface exists inside a browser document, so terminating the browser page already terminates the environment.

Commands will initially be case-insensitive. This preserves some of the convenience associated with classic command-line interfaces without requiring users to remember a particular capitalization.

The visual presentation, however, will deliberately retain elements of the classic DOS terminal aesthetic.

The result is not intended to reproduce DOS. It is a modern Internet-oriented environment presented through a familiar terminal metaphor.




Application arguments belong to the interface



The distinction between IOE and NetShell becomes especially important with command-line arguments.

IOE already provides an abstract input mechanism:


IOE.input.number('a');



This represents an application asking its environment for a number called `a`.

NetShell can provide another mechanism for supplying input through command-line arguments.



For example:


tricalc 3 4 1.5707963268



could provide:



3
4
1.5707963268



to the application.

This argument mechanism belongs to NetShell's interface rather than to the fundamental IOE protocol.

A different environment could provide the same application with its inputs through graphical controls, a dialog, a remote interface, or another mechanism.

The application therefore remains independent of the environment through which it is being operated.



This is an important property of the architecture:

IOE applications should depend on capabilities, not on a particular user interface.




The real purpose of NetShell



The purpose of NetShell is not to create a nostalgic terminal inside a web page.

The terminal is only the interface through which the underlying concept becomes visible.

The important question during its development will therefore be:

What would make someone genuinely want to use an IOE-based environment, rather than simply regard IOE as an interesting way of adding metadata to JavaScript files?



This question should guide the development of NetShell.



Every feature should be considered in terms of whether it demonstrates a meaningful advantage of treating Internet resources as interoperable computational resources.



For example:


    
  
  • Can an application be discovered without the environment knowing its implementation beforehand?
    • 
  
  • Can applications be loaded from outside the environment's own project?
    • 
  
  • Can independently hosted applications use independently hosted dependencies?
    • 
  
  • Can the same application operate through different interfaces?
    • 
  
  • Can the environment organize Internet resources in a way useful to the user?
    • 
  
  • Can an application become part of a larger computational workflow without being rewritten specifically for that environment?
    • 
  
  • Can the user interact with resources from different locations as though they belonged to one coherent computational environment?
    • 




These questions are more important than making NetShell increasingly elaborate.



A complicated terminal that only launches applications stored on one website would demonstrate relatively little.

A small terminal that can meaningfully consume independently distributed applications would demonstrate considerably more.




NetShell as a practical IOE environment



NetShell will therefore begin as a demonstration, but it is intended to evolve beyond the documentation.

The implementation developed from this section will eventually become a standalone project rather than remaining embedded inside this tutorial.

The documentation demonstrates the principles.

NetShell demonstrates their practical use.



The IOE protocol remains independent of both.



                 IOE
                  │
       ┌──────────┴──────────┐
       │                     │
   Applications          Environments
       │                     │

The final NetShell implementation will therefore not be reproduced in full inside this document.

Instead, this documentation will provide a link to the working NetShell environment.

This keeps the technical documentation focused on IOE itself while allowing NetShell to develop as a real piece of software.

The implementation can subsequently be published independently, versioned, forked, extended, and eventually distributed as a practical IOE-based tool.




Beyond the browser



The current IOE implementation necessarily operates within the capabilities exposed by the browser:


HTML
CSS
JavaScript
Browser networking
Browser execution environment



This is a limitation of the current implementation, not necessarily a limitation of the architectural idea.

IOE is being designed with the longer-term possibility of extending its environmental abstraction toward lower-level networking and computational environments.

Future implementations, forks, or contributions may therefore adapt the IOE model to environments that have access to capabilities unavailable to browser JavaScript, including other networking protocols and lower-level network interfaces.

The current project does not attempt to implement those capabilities.

Instead, the present implementation establishes the architectural boundary on which such future work can build.

The long-term objective is therefore not simply to create another JavaScript framework for websites.

It is to investigate how far the concept of an interoperable environment for Internet resources can be extended.

The browser is our current environment.

It does not have to be our final one.




From proof of concept to software



At this point, the purpose of the documentation changes.

The previous sections establish that the IOE model can be implemented.

NetShell establishes that the model can be used to construct a practical environment around it.

Once these demonstrations are complete, further development of IOE no longer needs to occur primarily as examples in this document.

The protocol can become software.

NetShell can become software.

Applications can become software.

And independent developers can begin experimenting with the system without needing to follow this tutorial to reproduce its implementation.



The documentation demonstrates the idea. The software puts the idea into practice.
